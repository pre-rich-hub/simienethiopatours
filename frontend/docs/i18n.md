# i18n translation plan

Step-by-step plan to finish Spanish (`es`), German (`de`), and French (`fr`) for every public catalogue entity. Work **one batch at a time** — do not translate the whole catalogue in one pass.

Related docs: [localization-review.md](./localization-review.md), [ethiopia-expansion.md](./ethiopia-expansion.md), [qa.md](./qa.md).

---

## 1. Scope

| Layer | Locales | Status (2026-10-06 audit) | Action |
|-------|---------|---------------------------|--------|
| UI chrome (`frontend/messages/*.json`) | en/es/de/fr | Complete (**852** keys each, Batch 11) | Human polish welcome |
| Gallery captions (`lib/gallery-captions.ts`) | es/de/fr | Present (42 pairs each) | Spot-check after catalogue work |
| Tours (catalogue / CMS) | en + es/de/fr | **34 × 4 locales** (Batches 3–8, 10) | Human review of machine copy |
| Destinations (catalogue / CMS) | en + es/de/fr | **58 × 4 locales** (Batches 1–2, 9) | Human review of machine copy |
| Journal posts | — | Empty in snapshot | Out of scope until posts exist |

English is the source of truth. ES/DE/FR live in CMS `ContentTranslation` rows (`status: published`, `reviewedAt` set). The frontend falls back to English when a locale row is missing or still contains English copy — that is what the client sees today.

---

## 2. Rules for this effort

1. **One batch per session** (or per PR). Mark the batch done before starting the next.
2. Translate **all three locales** (`es`, `de`, `fr`) for every slug in the batch before moving on.
3. Prefer **human-reviewed** marketing copy. Machine assist is OK as a draft; do not publish unreviewed English copies as “translated”.
4. Keep place names stable (Simien, Gondar, Ras Dashen, Debark, Fasil Ghebbi, etc.) unless a locale has an established local form.
5. After each batch: validate → export catalogue snapshot → spot-check the live pages.
6. Do **not** bulk-run `content:translations` over the whole catalogue without reviewing the batch first (it can overwrite or re-publish English-looking payloads if the source cache is wrong). Prefer admin Translations edit, or a **slug-scoped** seed/update when available.
7. Use slug filter: `npm run content:translations -- --slugs=slug-a,slug-b`.
8. If translations come back as English, clear those keys from `backend/scripts/data/translation-cache.json` (older runs cached English fallbacks) and re-run the batch.
9. Avoid full `content:export` until the local/staging DB contains the full catalogue (currently seed ≈ 32 destinations; snapshot ≈ 58). Prefer merging the batch’s translated rows into the existing snapshot.

## 3. Per-batch workflow (repeat every time)

### A. Prepare

1. Confirm you are on current `main` (or the agreed working branch).
2. Note the batch ID and slug list from [§4](#4-batches-do-in-order).
3. Open English source for each slug (admin CMS or `/en/...` page) and keep it beside the translation work.

### B. Translate

For each slug in the batch, for each of `es` / `de` / `fr`:

**Tours — translate every user-facing field:**

- `tourName`, `summary`, `overview`, `heroTitle`, `heroAccent`
- `itineraryIntro`, full `itinerary` (titles, bodies, overnight, stage labels/bodies)
- `highlights`, `included`, `excluded`, `route`, `preparation`, `itineraryNotes`
- `imageAlt` / notice copy if present

**Destinations — translate every user-facing field:**

- `name` (only if a real translation exists; otherwise keep proper noun)
- `heroTitle`, `heroAccent`, `overview`
- `highlights`, `thingsToDo`
- `alsoKnownAs`, `imageAlt` if present

Where to edit:

- **Preferred:** Admin → **Translations** → entity → locale → edit → mark reviewed → publish
- **Alternative:** Seed/update scripts under `backend/scripts/` only when scoped to this batch’s slugs

### C. Publish & export

From `backend/` (with DB credentials for the target environment):

```bash
# Coverage report (should shrink missing/English counts for this batch)
npm run content:localization -- -- ../frontend/lib/generated/catalogue.json

# After CMS publish is confirmed, refresh the frontend outage snapshot
npm run content:export
```

Commit the updated `frontend/lib/generated/catalogue.json` with the batch when that is the agreed release process.

### D. Verify

```bash
# Frontend UI key parity (should stay green)
cd frontend && npm run content:locale-audit

# Catalogue locale coverage
cd backend && npm run content:localization -- -- ../frontend/lib/generated/catalogue.json
```

Manual check (one slug per locale is enough per batch):

- `/es/<path>`, `/de/<path>`, `/fr/<path>` — headline + first itinerary/overview paragraph must **not** match English
- Language switcher keeps you on the same entity
- No accidental English dump in inclusions/highlights

### E. Mark progress

Update the checkboxes in [§4](#4-batches-do-in-order) and note date + reviewer in [§6](#6-progress-log).

## 5. Quick reference commands

```bash
# UI message key parity
cd frontend && npm run content:locale-audit

# Catalogue locale coverage (report)
cd backend && npm run content:localization -- -- ../frontend/lib/generated/catalogue.json

# Catalogue locale coverage (fail if any EN entity lacks es/de/fr)
cd backend && npm run content:localization -- --strict -- ../frontend/lib/generated/catalogue.json

# Export approved snapshot after CMS publish
cd backend && npm run content:export
```

Detect English leftovers for a slug (local helper — run from `frontend/`):

```bash
node -e '
const cat=require("./lib/generated/catalogue.json").catalogue;
const slug=process.argv[1];
for (const section of ["tours","destinations"]) {
  const rows=cat[section].filter(r=>r.slug===slug);
  if(!rows.length) continue;
  const en=rows.find(r=>r.locale==="en");
  for (const loc of ["es","de","fr"]) {
    const row=rows.find(r=>r.locale===loc);
    if(!row){ console.log(section, slug, loc, "MISSING"); continue; }
    const fields=["tourName","summary","overview","heroTitle","name","heroAccent"];
    const same=fields.filter(f=>en[f]&&en[f]===row[f]);
    console.log(section, slug, loc, same.length?("still EN: "+same.join(",")):"headlines OK");
  }
}
' -- <slug>
```

## 7. Definition of done

All of the following are true:

1. Every published tour and destination has reviewed `es` / `de` / `fr` rows.
2. Headline + body fields for those rows are not English copies (proper nouns excepted).
3. `content:localization --strict` passes against the exported snapshot.
4. `content:locale-audit` still passes for UI messages.
5. Client can open major hubs and a sample journey in ES/DE/FR without English body dump.
